# Архитектура и анализ: GameAP Discord WebMonitoring Bot

Документ описывает архитектурное решение, взвешивание рисков ("за" и "против"), модель безопасности и разделение зон ответственности между панелью GameAP, плагином WebMonitoring и Discord-ботом.

---

## 1. Взвешивание «ЗА» и «ПРОТИВ»

### Плюсы («ЗА»)
1. **Высокая ценность для игрового сообщества:** Игрокам не нужно открывать браузер или заходить в панель управления, чтобы узнать статус серверов, текущую карту или онлайн. Вся информация находится прямо в Discord.
2. **Нулевое влияние на ядро GameAP (Core):** Проект реализуется как автономный спутник (companion bot). Базовая панель GameAP не подвергается изменениям, обновлениям миграций или патчам ядра.
3. **Безопасная изоляция прав:** Бот работает строго в режиме чтения (Read-Only). Он не имеет доступа к RCON, консоли, файлам сервера или управлению питанием (Start/Stop).
4. **Интерактивность:** Discord поддерживает интерактивные кнопки под сообщениями (Components V2):
   - Кнопка **«Подключиться»** (`steam://connect/ip:port`).
   - Кнопка **«Обновить сейчас»** (ручной триггер обновления embed).
5. **Организация по темам:** В Discord есть форум-каналы (Forum Channels) и ветки (Threads), позволяющие автоматически создавать отдельную тему под каждую игру (CS2, Rust, TF2 и т.д.) или даже под каждый отдельный сервер.

### Минусы и риски («ПРОТИВ»)
1. **Необходимость отдельного сервиса (демона):** Бота нельзя запустить внутри WASM-плагина GameAP, так как плагины GameAP выполняются в изолированной песочнице Wazero и не могут держать постоянный входящий WebSocket-шлюз (Discord Gateway). Бот должен работать как отдельный фоновый процесс (systemd сервис или Docker-контейнер).
2. **Лимиты Discord API (Rate Limits):** Discord строго ограничивает частоту редактирования сообщений (не более 5 запросов в 5 секунд на один канал/вебхук). Попытка обновлять 20 серверов каждую секунду приведёт к HTTP 429 (Rate Limit ban). Решение: групповые карточки и интервал опроса 30–60 секунд.
3. **Хранение состояния (State Storage):** Боту необходимо где-то запоминать, в каком именно канале и сообщении он создал карточку сервера, чтобы при следующем тике редактировать именно её (`PATCH /messages/{id}`), а не спамить новыми сообщениями.

## 2. Где лучше настраивать: в Админ-панели или в Discord?

### Вердикт: Раздельная (гибридная) модель

Перегружать админ-панель GameAP настройками Discord (ID гильдий, ID каналов, токены бота, роли) — **плохая идея**, так как:
- Это усложняет веб-интерфейс плагина.
- При удалении/переименовании каналов в Discord администратору пришлось бы вручную лезть в GameAP и вбивать 19-значные цифровые ID Discord.

### Распределение зон ответственности:

| Где | Что настраивается | Почему именно там |
| :--- | :--- | :--- |
| **Админ-панель WebMonitoring** | 1. Галочка «Включить Bot API»<br>2. Кнопка «Сгенерировать секретный API-ключ» (`bot_api_key`)<br>3. Список разрешённых серверов (опционально) | Панель отвечает только за выдачу данных и защиту доступа. Никаких Discord ID и токенов бота в GameAP! |
| **Discord (через Слэш-команды бота)** | 1. Привязка к API панели: `/mon-setup url: https://... key: ...`<br>2. Выбор канала/форума для мониторинга: `/mon-bind channel: #servers`<br>3. Формат отображения: общая сводка или отдельные ветки по играм | В Discord работает удобный нативный селектор каналов, ролей и категорий прямо из интерфейса. |

## 3. Модель безопасности и обход 2FA GameAP

### Проблема
GameAP поддерживает двухфакторную аутентификацию (2FA) для учётных записей пользователей. Использование стандартной авторизации через логин/пароль/cookie для внешнего бота неприменимо.

### Архитектурное решение (Plugin API Token)
1. **Собственный защищённый эндпоинт плагина:**
   Плагин WebMonitoring предоставляет легковесный эндпоинт:
   `GET /api/plugins/monitoring/api/servers`
2. **Авторизация по Bearer-токену / заголовку:**
   Бот передаёт HTTP-заголовок:
   `X-WebMon-Token: <секретный_ключ_из_настроек_плагина>`
3. **Отсутствие привилегий управления:**
   Даже при компрометации ключа бота злоумышленник сможет получить только публичную информацию о серверах (IP, порт, онлайн, карта). Управлять серверами GameAP через этот ключ невозможно.
4. **Фильтрация серверов:**
   Бот получает только те серверы, которые администратор явно разрешил показывать в мониторинге (учитывается флаг видимости из настроек плагина).

## 4. Сценарии отображения в Discord

### Сценарий А: «Единое табло» (Single Dashboard Channel)
- Создаётся один канал `#мониторинг-серверов`.
- Бот создаёт 1–3 красивых сводных Embed-сообщения (по играм).
- Каждые 30–60 секунд бот редактирует эти сообщения.
- Под каждым сообщением кнопки «Подключиться».

### Сценарий Б: «Форум-канал / Темы» (Forum Channels & Threads)
- В Discord создаётся Forum Channel `#игровые-серверы`.
- Бот создаёт темы по названиям игр (например, тег "Counter-Strike 2", тег "Rust").
- Внутри каждой темы закреплён первый пост со статусом серверов данной игры.
- Игроки могут в этой же теме обсуждать сервер, искать тиммейтов и видеть онлайн.

### Сценарий В: «Персональный канал на каждый сервер» (Dedicated Per-Server Channel Routing)
- **Цель:** Игровой проект имеет отдельные текстовые каналы под каждый свой флагманский сервер:
  - 💬 `#cs2-mirage` ➔ персональная живая карточка Сервера #1
  - 💬 `#cs2-retake` ➔ персональная живая карточка Сервера #2
  - 💬 `#rust-main-x5` ➔ персональная живая карточка Сервера #3
  - 💬 `#minecraft-vanilla` ➔ персональная живая карточка Сервера #4
- **Идентификация серверов:** Используется нативный системный числовой ID из базы GameAP (`server.id: uint64`, например `1, 2, 3...`). Он неизменен, уникален и транслируется плагином в JSON API.
- **Привязка:** Настраивается через `config.json` (`server_channels`), либо через Discord слэш-команду `/mon-bind server: <id> channel: <#channel>` и сохраняется в `state.json`.
- **Обновление:** Бот опрашивает `/api/servers`, находит привязанный канал и сообщение сервера, выполняя точечный `PATCH /messages/{id}`.

### 4.3 Унифицированный макет персональной карточки сервера (Single Server Embed)
Сетка 2x3, адаптированная под интерактивные компоненты Discord v2. Из макета исключён пинг (избыточен и не отражает задержку игрока), а превью карт заменено на **каталог официальных иконок игр**:

```text
┌────────────────────────────────────────────────────────────────────────┐
│ ▌ 🎮 ★ CyberZone CS2 | Mirage 24/7 [128 Tick]       ┌───────────────┐ │
│ ▌ Консоль: `connect 198.51.100.10:27015`            │  [Логотип     │ │
│ ▌                                                   │   игры CS2]   │ │
│ ▌ Статус              Адрес и порт          Локация │  (Thumbnail)  │ │
│ ▌ 🟢 В сети           `198.51.100.10:27015` 🇩🇪 DE   └───────────────┘ │
│ ▌                                                                     │
│ ▌ Игра                Текущая карта         Игроки                    │
│ ▌ Counter-Strike 2    Mirage (de_mirage)    18/32 [██████░░░░]        │
│ ▌                                                                     │
│ ▌ 🌐 GameAP WebMonitoring • Обновлено <t:TIMESTAMP:R>                 │
└────────────────────────────────────────────────────────────────────────┘
  [ 🎮 Подключиться ]   [ 🔄 Обновить ]
```

- **Кнопки под карточкой:**
  - `[ 🎮 Подключиться ]`: отправляет эфемерное всплывающее сообщение со ссылкой `steam://` и готовой командой `connect ip:port` для копирования (обход блокировок кастомных схем в мобильном Discord).
  - `[ 🔄 Обновить ]`: мгновенный опрос и обновление карточки конкретного сервера.
- **Относительный таймстамп:** нативный синтаксис `<t:timestamp:R>` (автоматический пересчёт времени клиентом Discord).
- **Индикатор слотов:** визуальный прогресс-бар `18/32 [██████░░░░]`.
- **Иконка игры (Game Catalog Thumbnail):** логотип игры в правом верхнем углу из каталога иконок (Steam CDN / статический репозиторий) вместо нестабильных превью карт.
- **Исключение пинга:** сетевая задержка (пинг) исключена из дизайна, так как пинг до ноды зависит от провайдера каждого конкретного пользователя и только перегружает интерфейс.

## 5. Выбор технологического стека для Бота

1. **Вариант 1 (Рекомендуемый): Go (Golang) + `bwmarrin/discordgo`**
   - **Плюсы:** Компилируется в один статический бинарник (`gameap-webmon-bot.exe` под Windows или `webmon-bot` под Linux).
   - **Потребление ресурсов:** 10–20 МБ RAM.
   - **Развёртывание:** Запуск одной строкой или как сервис systemd/Docker. Идеальное соответствие экосистеме Go-плагинов GameAP.
2. **Вариант 2: Python + `disnake` / `discord.py`**
   - **Плюсы:** Быстрая модификация без перекомпиляции.
   - **Минусы:** Требует установленного окружения Python и зависимостей (`pip install ...`).
3. **Вариант 3: Node.js + `discord.js`**
   - **Плюсы:** Популярный стек для Discord-ботов.
   - **Минусы:** Память от 60–100 МБ, зависимость от `node_modules`.

## 6. Система событий и оперативных алертов (Server Life-cycle & Alerting)

Помимо цикличного обновления дашборда (live-card), бот отслеживает жизненный цикл и изменения состояния серверов, генерируя целевые уведомления в выделенный канал событий (например, `#серверные-логи` или `#server-alerts`).

### 6.1 Отслеживаемые события

| Событие | Триггер / Условие детекции | Цвет Embed | Описание в сообщении |
| :--- | :--- | :--- | :--- |
| 🔴 **Выключение / Падение (Offline / Down)** | Статус сменился с `online` на `offline` и держится $N$ проверок подряд | Красный (`#e74c3c`) | Название, IP:порт, время фиксации падения. Опционально: упоминание роли админов. |
| 🟢 **Восстановление / Запуск (Online / Recovered)** | Статус сменился с `offline` на `online` | Зеленый (`#2ecc71`) | Название, IP:порт, время восстановления, длительность простоя (downtime). |
| 🔄 **Перезагрузка (Restart Detected)** | Кратковременный оффлайн с последующим онлайном, либо сброс счетчика онлайна/аптайма | Желтый (`#f1c40f`) | «Сервер перезагружен и снова принимает игроков». |
| 📦 **Обновление сервера / игры (Update / Maintenance)** | Изменение версии сборки (`version` / `build_id`) или статус техработ / обновления в API GameAP | Синий (`#3498db`) | Номер версии / статус обновления: «Сервер обновлен до версии X.Y.Z». |

### 6.2 Защита от ложных срабатываний (Anti-Flapping & De-bounce)

В UDP-запросах игровых серверов возможны единичные потери пакетов (micro-packet-loss) или временные задержки сети:
- **Порог подтверждения оффлайна (`offline_confirm_threshold`):** Бот не отправляет алерт о падении моментально при первом сбое. Статус считается падением только после **2–3 подряд** неудачных опросов (например, 60–90 секунд устойчивого оффлайна).
- **Кулдаун на повторные алерты:** Предотвращает спам, если сервер циклично рестартится или завис в boot-loop.

### 6.3 Модель доставки уведомлений

1. **Канал алертов:** Рекомендуется отдельный текстовый канал (`alerts_channel_id`), чтобы не засорять основной информационный канал дашборда.
2. **Пинги ролей:** Опциональная настройка `alert_role_id` — пингует дежурных администраторов только при критическом событии (падении).
